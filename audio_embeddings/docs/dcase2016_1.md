# DCASE 2016 Task 1: prepare audio, extract features, and run AL sweeps

This workflow uses the DCASE Task 1 development set in `data/datasets/DCASE-2016-1`, the existing DCASE manifest builder, and the SSAST/BEATs active-learning sweep configs under `configs/dcase2016_1/`.

## Dataset files and metadata

The release's eight `.zip` files under `audio/` are source archives. They are not the compact archives produced by this project's `pack-audio` command. The source ZIPs contain WAV files named like `b109_90_120.wav`; extract them into the existing `audio/` directory so manifest paths such as `audio/b109_90_120.wav` resolve.

Run on the remote host from the repository's parent directory, adjusting `PROJECT_ROOT` if needed:

```bash
export PROJECT_ROOT=/cs/labs/daphna/yael.bs444/projects/daphna_lab/audio_embeddings
export DATASET_ROOT="$PROJECT_ROOT/data/datasets/DCASE-2016-1"
cd "$(dirname "$PROJECT_ROOT")"

for archive in "$DATASET_ROOT"/audio/*.zip; do
  unzip -n "$archive" -d "$DATASET_ROOT/audio"
done

python "$PROJECT_ROOT/data/prepare_dcase2016_task1_metadata.py" \
  --dataset-root "$DATASET_ROOT" --check-audio

python -m audio_embeddings manifest \
  --dataset dcase2016-1 \
  --root "$DATASET_ROOT" \
  --metadata "$DATASET_ROOT/metadata/dcase2016_task1.csv" \
  --output "$DATASET_ROOT/dcase2016_1.jsonl"
```

The metadata helper combines `metadata/meta.txt` with each `foldN_train.txt` and `foldN_test.txt`. It checks that every train/test pair partitions the labeled release metadata and that each recording belongs to exactly one held-out test fold. The output has the columns required by this package: `recording_id,audio_path,scene,fold`. `--check-audio` also verifies the WAVs are extracted. The expected manifest contains 1,170 recordings across four held-out folds.

You can run the manifest builder again after regenerating the CSV. Keep the generated CSV and JSONL manifest with the dataset; the feature cache records the manifest checksum, so changing the manifest means regenerating the feature cache.

## Reusable feature cache for the sweep configs

The configs set `feature_cache` to a finalized cache shared by every sweep job for that model and dataset. To populate those caches, use the package's compact-audio workflow. You only need to run `pack-audio` once for DCASE; the resulting audio index and archives can be used for both models.

```bash
python -m audio_embeddings pack-audio \
  --manifest "$DATASET_ROOT/dcase2016_1.jsonl" \
  --output "$DATASET_ROOT/compact" --batch-size 500
```

The `.tar.zst` batches and `audio_index.json` created here are the format accepted by `extract-array`. For example, prepare and submit SSAST extraction:

```bash
python -m audio_embeddings extract-array \
  --manifest "$DATASET_ROOT/dcase2016_1.jsonl" \
  --audio-index "$DATASET_ROOT/compact/audio_index.json" \
  --model ssast \
  --checkpoint "$PROJECT_ROOT/models_src/SSAST/pretrained_model/SSAST-Base-Frame-400.pth" \
  --checkpoint-metadata "$PROJECT_ROOT/models_src/SSAST/pretrained_model/ssast_pretrained.provenance.json" \
  --output "$PROJECT_ROOT/features/dcase2016-1-ssast" \
  --job-dir "$PROJECT_ROOT/slurm/dcase2016-1-ssast-extract" \
  --batch-size 16 --device cuda \
  --temporary-root /scratch/yael.bs444/audio-extract \
  --activate /cs/labs/daphna/yael.bs444/projects/daphna_lab/.venv-audio/bin/activate \
  --working-directory /cs/labs/daphna/yael.bs444/projects/daphna_lab \
  --submit
```

Run the corresponding BEATs extraction separately. Both arrays can read the same compact audio index:

```bash
python -m audio_embeddings extract-array \
  --manifest "$DATASET_ROOT/dcase2016_1.jsonl" \
  --audio-index "$DATASET_ROOT/compact/audio_index.json" \
  --model beats \
  --checkpoint "$PROJECT_ROOT/models_src/BEATs/ckpts/BEATs_iter3_plus_AS2M.pt" \
  --checkpoint-metadata "$PROJECT_ROOT/models_src/BEATs/ckpts/beats_pretrained.provenance.json" \
  --output "$PROJECT_ROOT/features/dcase2016-1-beats" \
  --job-dir "$PROJECT_ROOT/slurm/dcase2016-1-beats-extract" \
  --batch-size 16 --device cuda \
  --temporary-root /scratch/yael.bs444/audio-extract \
  --activate /cs/labs/daphna/yael.bs444/projects/daphna_lab/.venv-audio/bin/activate \
  --working-directory /cs/labs/daphna/yael.bs444/projects/daphna_lab \
  --submit
```

Finalize each model separately after its array succeeds:

```bash
python -m audio_embeddings finalize-extract \
  --manifest "$DATASET_ROOT/dcase2016_1.jsonl" \
  --audio-index "$DATASET_ROOT/compact/audio_index.json" \
  --output "$PROJECT_ROOT/features/dcase2016-1-ssast"

python -m audio_embeddings finalize-extract \
  --manifest "$DATASET_ROOT/dcase2016_1.jsonl" \
  --audio-index "$DATASET_ROOT/compact/audio_index.json" \
  --output "$PROJECT_ROOT/features/dcase2016-1-beats"
```

The resulting cache locations (`<output>/feature_cache`) match the DCASE configs. Then submit each AL sweep:

```bash
python -m audio_embeddings sweep \
  --config "$PROJECT_ROOT/configs/dcase2016_1/ssast_al_hps_sweep.yaml" \
  --job-dir /cs/labs/daphna/yael.bs444/outputs/slurm/dcase2016-1-ssast-hps \
  --submit

python -m audio_embeddings sweep \
  --config "$PROJECT_ROOT/configs/dcase2016_1/beats_al_hps_sweep.yaml" \
  --job-dir /cs/labs/daphna/yael.bs444/outputs/slurm/dcase2016-1-beats-hps \
  --submit
```

## Direct extraction without `pack-audio`

If the WAVs are extracted and visible on the same machine, `extract` can read the manifest's paths directly. This avoids `pack-audio` and `extract-array` for a one-off embedding run:

```bash
python -m audio_embeddings extract \
  --manifest "$DATASET_ROOT/dcase2016_1.jsonl" \
  --model ssast \
  --checkpoint "$PROJECT_ROOT/models_src/SSAST/pretrained_model/SSAST-Base-Frame-400.pth" \
  --checkpoint-metadata "$PROJECT_ROOT/models_src/SSAST/pretrained_model/ssast_pretrained.provenance.json" \
  --output "$PROJECT_ROOT/features/dcase2016-1-ssast-direct" \
  --batch-size 16 --device cuda
```

The command prints an immutable extraction run directory. Direct extraction does not produce the finalized `feature_cache` expected by the supplied sweep configs; those configs validate a completed cache before sharing it across jobs. For a one-off `run-al`, omit `feature_cache` from a run config and it extracts inline. For the multi-job sweeps, use the compact extraction/finalization sequence above so the embeddings are computed once and reused.

Each DCASE recording is 30 seconds. The extractor splits it into fixed windows (10.24 seconds for SSAST, 10 seconds for BEATs) and averages the window embeddings into one vector per recording. It does not need DCASE-specific audio-loading changes.

## Config notes

- `configs/dcase2016_1/ssast_al_hps_sweep.yaml` and `beats_al_hps_sweep.yaml` use folds 1–4 and budgets as percentages of the eligible training pool.
- Each model has a separate feature cache and experiment output directory. Do not point BEATs at the SSAST cache.
- The BEATs configs expect a provenance JSON at `models_src/BEATs/ckpts/beats_pretrained.provenance.json`, with the fields required by `training/trainer_al.py`. If your remote provenance file is elsewhere, update `model.checkpoint_metadata` in both BEATs configs.
- All paths used by a SLURM job must be visible on every node. Keep the source ZIPs until WAV extraction has completed, and keep compact `.tar.zst` batches until extraction finalization and retries are complete.
